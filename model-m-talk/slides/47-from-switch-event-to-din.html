Follow one concrete melody key. At priority 15, the switch state machine sees the second threshold and creates SwitchEvent::NoteOn with a computed velocity. timer_handler pairs that semantic event with the switch index and puts it in the fixed 64-entry queue. It then spawns process_events and returns to its scan work. At priority 2, process_events looks up the musical note, applies the octave setting, selects the melody or drum channel, and calls MidiSender. For switch zero at the default octave setting and velocity 100, the table's note 78 is transposed down two octaves to note 54, hexadecimal 0x36, on channel 1: bytes 90 36 64. MidiSender blocks while the UART serializes those bytes, but only in the low-priority task. This is why MIDI never steals the one-millisecond scan deadline. Be explicit about the current receive limitation: bytes are drained only to show activity on LED2; there is no MIDI parser or thru behavior yet.
